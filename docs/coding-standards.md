# コーディング規約

この規約は、機能を追いやすくし、初心者が処理の順番と変更点を理解できることを目的とします。コメントはコードの一行ごとではなく、理由・入力・出力・副作用が読み取りにくい箇所に付けます。

## Java

- クラス名は `UpperCamelCase`、メソッドと変数は `lowerCamelCase`、定数は `UPPER_SNAKE_CASE` にします。
- Javaの整形はSpotless経由のGoogle Java Formatに統一します。`./gradlew spotlessApply` で整形し、`./gradlew spotlessCheck` で差分を確認します。
- HTML、CSS、JavaScript、Markdownはローカル固定バージョンのPrettierで整形します。`npm run format` で整形し、`npm run format:check` で確認します。
- クラスは単一の責務を持たせ、HTTP 入出力、認証、データ変換、永続化を可能な範囲で分離します。
- コンストラクター注入を優先し、依存をフィールド内で直接生成する箇所を新規に増やしません。Lambda ハンドラーではテスト容易性を保てるよう、必要なら既定コンストラクターとテスト用コンストラクターを用意します。
- 入力は境界で検証し、API の利用者に内部例外や秘密情報を返しません。内部ログにもトークンや個人情報を記録しません。
- `null` を返すより、空コレクション、明示的な結果型、または適切な例外を使います。共有される変更不能データには `List.copyOf` / `Map.copyOf` を検討します。
- `try-with-resources` を使い、クライアントやストリームの寿命を明確にします。長寿命の AWS SDK クライアントを Lambda 呼び出しごとに作り直さないようにします。
- 日時は `java.time` を使い、文字列から日時への変換は厳密に行います。タイムゾーンの前提を API・設計書に明示します。
- 公開クラスと公開メソッドには Javadoc を付けます。目的、引数、返却値、例外、権限や副作用など利用者が必要とする契約を記載します。
- コメントは「何をしているか」の逐語訳でなく、「なぜこの条件が必要か」「データがどう流れるか」を説明します。
- 例外を握りつぶさず、呼び出し元が扱える API エラーに変換します。クライアントに返す文面と内部診断情報を分けます。

## JavaScript

- `const` を既定とし、再代入が必要なものだけ `let` を使います。`var` と暗黙のグローバル変数は使いません。
- DOM、API、表示、認証の処理を名前付き関数に分け、関数名から目的が分かるようにします。
- 非同期処理は `async` / `await` と `try` / `catch` を使い、ローディング、成功、失敗の表示をそろえます。
- ユーザーや API から受け取った文字列を `innerHTML` に入れる前に必ずエスケープします。静的テキストには `textContent` を使います。
- UI の権限判定は操作導線の制御に限り、API で認証・認可を必ず再検証します。
- URL、日付、数値、CSV の入力は境界で検証し、曖昧な暗黙変換に依存しません。
- 関数には必要に応じて JSDoc で引数・戻り値・副作用を説明します。意図の読み取りに時間がかかる分岐には短い日本語コメントを付けます。
- イベントリスナーの登録は初期化関数にまとめ、ページ再初期化時に多重登録しないようにします。

## HTML

- `header`、`nav`、`main`、`section`、`footer` など意味に合った要素を使います。
- 各ページに一意な `h1`、日本語ページの `lang="ja"`、フォームの明示的な `label` を用意します。
- 操作ボタンには `type="button"` または `type="submit"` を明記し、クリック領域と名前をスクリーンリーダーに伝えます。
- インライン CSS とインラインイベント属性を増やさず、スタイルは CSS、動作は JavaScript に置きます。
- 状態を色だけで伝えず、テキスト、アイコン、`aria-live`、`aria-current` 等も使います。
- 動的に開閉する領域は `hidden`、`aria-expanded`、`aria-controls` を状態に合わせます。

## CSS

- レイアウト、部品、テーマを分け、共有デザイン値は CSS カスタムプロパティで管理します。
- ページ名・コンポーネント名を含むクラスを使い、HTML 要素全体への広すぎる上書きを避けます。
- `!important`、インラインスタイル、過剰な詳細度を新規に増やしません。既存スタイルを整理するときはテーマと画面幅の上書きを確認します。
- モバイル幅、キーボードフォーカス、無効状態、ダークモードを合わせて確認します。
- 色だけに状態を依存せず、十分なコントラストと明確なフォーカスリングを維持します。
- 画面遷移や選択の動きは短く控えめにし、`prefers-reduced-motion` が有効な端末ではアニメーションを抑えます。

## 変更と検証

- 1変更単位で関係する画面、API、権限、ドキュメント、テストを一緒に更新します。
- 認可・データ変換・入力境界には自動テストを追加します。フロントエンドは JavaScript 構文と主要な画面操作を確認します。
- `./gradlew clean test javadoc` と全 JavaScript の `node --check` を実行します。HTML/CSS の構文・アクセシビリティ検査を導入した場合は、そのコマンドも実行します。
- 実行できなかった確認は理由を記録し、成功したように報告しません。
- API、画面、データモデル、AWS 接続が変わったら関連する `docs/` を更新します。
