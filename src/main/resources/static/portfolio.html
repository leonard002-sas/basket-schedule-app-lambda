01 / PROBLEM

連絡と記録が分散する

予定、施設、周知、出欠、動画、試合結果が別々に管理され、確認と更新に手間がかかっていました。

02 / APPROACH

利用の流れでつなぐ

予定を中心に、出欠・施設・動画・試合記録へ移動できる情報設計と、権限別の操作を設計しました。

03 / CURRENT STATE

ひとつのチームサイトへ

運営者が登録し、メンバーが確認・回答できる場所として、実際の利用を通じて継続改善しています。

CAL

予定・施設

練習、試合、会議をカレンダーで共有。繰り返し登録やGoogleカレンダー出力にも対応。

RSVP

出欠・周知

参加・未定・不参加をまとめて回答。緊急度と期限を持つ周知事項も掲載。

AI

画像から予定登録

S3へ直接アップロードし、Geminiで解析。処理状況を見ながら別の作業を継続可能。

PTS

試合・スタッツ

試合中に選手を切り替えて記録。DNPを考慮した出場試合数・平均・ランキングを集計。

VID

練習動画

YouTube限定公開URLを予定に紐づけ、タグで整理して後から振り返れる構成。

IAM

ユーザー・権限

Cognito認証、参加承認、管理者・メンバー権限、Googleログイン連携を実装。

03

ENGINEERING

設計と運用の判断

画面を完成させるだけでなく、使い続けるための安全性、速度、費用、変更しやすさまで扱っています。

SERVERLESS ARCHITECTURE

必要なときだけ動く、
小さなAWS構成。

静的画面はS3とCloudFront、APIはJava Lambda、データはDynamoDBに分離。個人開発でも維持しやすく、アクセス量に応じた費用になる構成を選びました。

AUTHORIZATION

画面とAPIの二重チェック

管理者向けUIを隠すだけでなく、Lambda側でもトークンとCognitoグループを検証します。

ASYNC PROCESSING

重い処理を画面から分離

画像解析はS3イベントで非同期実行し、画面はジョブ状態を確認する構成にしています。

COST CONTROL

固定費を持ちにくい選択

サーバーレス構成と直接S3アップロードで、Lambdaの処理時間とデータ転送を抑えます。

DELIVERY

プッシュから自動反映

Gradleビルド、Lambda更新、S3同期、CloudFrontキャッシュ削除までCodePipelineで実行します。

04

QUALITY & DOCUMENTATION

つくった後も、説明できる状態に。

01レスポンシブUI

PCとスマートフォンの双方で、同じ情報へ迷わずアクセスできる設計。

02状態のフィードバック

03テストと整形

04設計ドキュメント

ABOUT THE WORK

自分の暮らしから、
プロダクトを考える。

バスケサークルを運営する中で感じた不便や、婚約後の生活で必要になったことを出発点にしています。自分が利用者でもあるからこそ、実際の操作で感じた違和感を次の改善につなげています。
